`selo test` writes up to four outputs. Three are safe to publish. The run state file is not, because it holds the private report link.

| Output | Written when | Holds | Safe to publish |
| --- | --- | --- | --- |
| [`.selo/runs/<release>.json`](#the-run-state-file) | Before the paid route is contacted, and again after every attempt | Recovery state, including the private report link | No |
| [`--summary <file>`](#the-gate-summary) | After every attempt that reaches the payment stage, when `--summary` is set | The `selo.gate.v1` summary, with the report link redacted | Yes |
| [`--attestation <file>`](#the-attestation-file) | When Selo returns a signed attestation and `--attestation` is set | Selo's Ed25519-signed attestation | Yes |
| [`GITHUB_STEP_SUMMARY`](#github-step-summary) | After every attempt that reaches the payment stage, when the variable is set | The summary as Markdown, appended | Yes |

A run that stops at input validation, at the run state check or at the preflight writes none of them. Relative paths resolve against the directory you ran the command in.

## The run state file

`selo test` records each paid attempt in `.selo/runs/<release>.json`, where `<release>` is the `--release` value. The CLI uses it to refuse a second payment while an earlier outcome is unconfirmed, and to resume that attempt with `--resume`.

- **Location:** `.selo/runs/` under the directory you ran the command in. The directory is created with mode `700`.
- **Permissions:** the file is written with mode `600`, atomically, through a `.tmp` file that is renamed into place.
- **One file per release:** a new run for the same release replaces the file.
- **Format:** pretty-printed JSON. Any extra or missing field makes the file unreadable to the CLI.

<Warning>
Never upload `.selo/` as a CI artifact or commit it. The `reportUrl` field holds the full private report link.
</Warning>

### Fields

<ResponseField name="schema" type="string" required>
  Always `selo.cli.run.v1`.
</ResponseField>
<ResponseField name="release" type="string" required>
  The `--release` value. Also the file name.
</ResponseField>
<ResponseField name="api" type="string" required>
  The `--api` origin, for example `https://api.useselo.xyz`.
</ResponseField>
<ResponseField name="target" type="object" required>
  The endpoint under test.
  <Expandable title="properties">
    <ResponseField name="url" type="string" required>
      The normalized `--url`.
    </ResponseField>
    <ResponseField name="method" type="string" required>
      `GET` or `POST`.
    </ResponseField>
  </Expandable>
</ResponseField>
<ResponseField name="network" type="string" required>
  `algorand-mainnet` or `algorand-testnet`.
</ResponseField>
<ResponseField name="payer" type="string" required>
  The payer wallet's Algorand address. Never the mnemonic.
</ResponseField>
<ResponseField name="preflightId" type="string" required>
  The preflight the attempt pays for. `--resume` reuses it.
</ResponseField>
<ResponseField name="idempotencyKey" type="string" required>
  `selo-cli-` followed by the first 48 hex characters of the SHA-256 of `<preflightId>:<payer>`. `--resume` sends it again so Selo never settles a duplicate.
</ResponseField>
<ResponseField name="phase" type="string" required>
  `paying`, `unresolved`, `rejected` or `concluded`. See [Phases](#phases).
</ResponseField>
<ResponseField name="message" type="string" required>
  Why the run is in this phase: `the paid request is being sent` while paying, otherwise the same reason the gate line and the summary show.
</ResponseField>
<ResponseField name="expectedInboundTxId" type="string | null" required>
  The transaction id of your payment to Selo, computed from the signed payment before it was sent. Look it up on an Algorand explorer when an outcome is unconfirmed. `null` when nothing was signed. A resumed run keeps the id recorded first.
</ResponseField>
<ResponseField name="jobId" type="string | null" required>
  Selo's job id, when a report came back.
</ResponseField>
<ResponseField name="verdict" type="string | null" required>
  `PASS`, `FAIL` or `INCONCLUSIVE` as reported, when a report came back.
</ResponseField>
<ResponseField name="reportUrl" type="string | null" required>
  The full, private report link, when a report came back. This is the only place the CLI keeps it.
</ResponseField>
<ResponseField name="updatedAt" type="string" required>
  When the file was last written, as an ISO 8601 timestamp.
</ResponseField>

```json .selo/runs/<release>.json
  "release": "<your release id>",
  "api": "https://api.useselo.xyz",
  "target": {
    "url": "https://staging.example.com/v1/orders",
    "method": "POST"
  },
  "network": "algorand-mainnet",
  "payer": "<payer address>",
  "preflightId": "pfl_…",
  "idempotencyKey": "selo-cli-<48 hex characters>",
  "phase": "concluded",
  "message": "PASS on every release check",
  "expectedInboundTxId": "<transaction id>",

  "verdict": "PASS",
  "reportUrl": "https://api.useselo.xyz/v1/reports/<private token>",
  "updatedAt": "<ISO 8601 timestamp>"
}
```

### Phases

| Phase | Meaning | Blocks a new paid run | `--resume` |
| --- | --- | --- | --- |
| `paying` | Written just before the CLI contacts the paid route. If the CLI stops before it records an outcome, the file keeps this phase. | Yes | Allowed |
| `unresolved` | The payment was sent and its outcome is not confirmed: no answer, a redirect, a `5xx`, a held settlement, a job still in progress, or any refusal while resuming. | Yes | Allowed |
| `rejected` | Nothing was charged: the CLI refused before signing, Selo could not be reached before payment, or Selo refused the paid request (`402`, `FACILITATOR_UNAVAILABLE`, another `4xx`). | No | Refused: `the last run for release <release> is already rejected: …` |
| `concluded` | Selo answered with a report, with an answer that is not a report, or with `JOB_TERMINAL`. | No | Refused: `the last run for release <release> is already concluded: …` |

While the phase is `paying` or `unresolved`, every `selo test` for that release prints recovery instructions and exits `2` without contacting Selo. See [Resuming an unconfirmed run](/cli/test#resuming-an-unconfirmed-run) and [Recover an interrupted run](/guides/resume).

<Warning>
The CLI never clears a `paying` or `unresolved` run on its own. Removing or editing the file removes that protection: the next run starts a new preflight and pays again. Do it only after you have checked on chain whether the earlier payment settled.
</Warning>

If the file exists but cannot be read or does not match the shape above, every run for that release exits `2` with `the run state <path> is unreadable; inspect it before paying again`.

## The gate summary

`--summary <file>` writes a `selo.gate.v1` JSON summary: the gate decision, the verdict, every check, both payment legs and the job id. The report link is redacted, so the file is safe to upload as a CI artifact. Parent directories are created, and an existing file is overwritten.

## The attestation file

`--attestation <file>` saves the signed attestation that Selo returns with the report, exactly as received, as pretty-printed JSON. It holds no secret and is safe to publish. [`selo verify`](/cli/verify) checks it offline. When Selo returns no attestation, the CLI prints `attestation none: Selo issued no signed attestation for this run` and writes nothing.

The file is an envelope `{ payload, signature }`. The signature is Ed25519 over the canonical JSON of `payload`: object keys sorted at every level, no whitespace. See [Signed attestations](/concepts/attestations).

### Fields

<ResponseField name="payload" type="object" required>
  The signed statement.
  <Expandable title="properties">
    <ResponseField name="schemaVersion" type="string" required>
      `selo.release.v1`.
    </ResponseField>
    <ResponseField name="issuer" type="string" required>
      The Selo deployment that signed it, for example `https://api.useselo.xyz`.
    </ResponseField>
    <ResponseField name="jobId" type="string" required>
      Selo's job id.
    </ResponseField>
    <ResponseField name="testedTarget" type="object" required>
      `url` and `method` of the endpoint Selo tested.
    </ResponseField>
    <ResponseField name="deployment" type="object | null" required>
      `id` (the release you asserted) and `verification` (always `asserted_by_client`), or `null` when no release was sent.
    </ResponseField>
    <ResponseField name="testedAt" type="string | null" required>
      When the job started.
    </ResponseField>
    <ResponseField name="completedAt" type="string" required>
      When the job completed.
    </ResponseField>
    <ResponseField name="seloVersion" type="string" required>
      The commit of Selo that ran the test, or `unknown`.
    </ResponseField>
    <ResponseField name="verdict" type="string" required>
      `PASS`, `FAIL` or `INCONCLUSIVE`.
    </ResponseField>
    <ResponseField name="inconclusiveReason" type="string | null" required>
      Why the verdict is INCONCLUSIVE, otherwise `null`.
    </ResponseField>
    <ResponseField name="checks" type="object[]" required>
      Each check's `id`, `status`, `code`, `blocking` flag and `evidence` ids.
    </ResponseField>
    <ResponseField name="expectedContractSha256" type="string | null" required>
      SHA-256 of the canonical JSON of your release contract, or `null` when none was sent.
    </ResponseField>
    <ResponseField name="targetChallengeSha256" type="string | null" required>
      The SHA-256 of your endpoint's 402, as recorded in the `target_challenge` evidence row, or `null`.
    </ResponseField>
    <ResponseField name="payments" type="object" required>
      `network` (CAIP-2), `asset` (the USDC ASA id), `inboundTxId`, `inboundAmountUsdc`, and `downstream`: one entry per payment Selo made to your endpoint, with `status`, `amountUsdc` and `txId`.
    </ResponseField>
    <ResponseField name="evidenceSha256" type="string" required>
      SHA-256 of the canonical JSON of the `evidence` manifest.
    </ResponseField>
    <ResponseField name="evidence" type="object[]" required>
      The evidence manifest, sorted by id: each row's `id`, `kind` (for example `target_challenge`, `paid_response`, `replay_response`, `downstream_payment`) and `sha256`.
    </ResponseField>
  </Expandable>
</ResponseField>
<ResponseField name="signature" type="object" required>
  <Expandable title="properties">
    <ResponseField name="algorithm" type="string" required>
      `Ed25519`.
    </ResponseField>
    <ResponseField name="keyId" type="string" required>
      The signing key, for example `selo-ed25519-728fcf85650b128f`. Match it against your pinned key set.
    </ResponseField>
    <ResponseField name="value" type="string" required>
      The signature, base64url-encoded.
    </ResponseField>
  </Expandable>
</ResponseField>

## GitHub step summary

When the `GITHUB_STEP_SUMMARY` environment variable is set, `selo test` appends the summary to that file as Markdown. GitHub Actions sets the variable for every step and renders the file on the run's summary page. Each run appends one block: a heading with the gate, the reason in bold, a table of the release, target, network, verdict, both payment legs and the job, then one row per check. The checks table is left out when no report came back. Pipes in values are escaped and line breaks become spaces.

## What is redacted

| Value | Terminal | `--summary` | `GITHUB_STEP_SUMMARY` | Run state | Attestation |
| --- | --- | --- | --- | --- | --- |
| Payer mnemonic | Never | Never | Never | Never | Never |
| Signed payment | Never | Never | Never | Never | Never |
| Report link token | Redacted | Redacted | Not included | Full link | Not included |
| Payer address | Printed | Not included | Not included | Stored | Not included |
| Transaction ids, job id, verdict, checks | Printed | Included | Included | Job id, verdict and expected inbound transaction id | Included |

## Input files

For completeness, the files the CLI reads:

| File | Flag | Limits | Reference |
| --- | --- | --- | --- |
| Release contract | `selo test --contract` | JSON object with only `status`, `contentType`, `jsonSchema`; file at most 64 KiB; schema compiled in strict mode, at most 16 KiB | [Write a release contract](/guides/release-contract) |
| Request body | `selo preflight --body`, `selo test --body` | Any JSON value but `null`; file at most 64 KiB; at most 16 KiB once serialized; `POST` only | [selo test flags](/cli/test#flags) |
